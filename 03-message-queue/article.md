# 延时队列：订单超时自动取消

> 目标：从"定时轮询"这个最朴素的方案出发，一关一关升级到延时队列，对齐 RabbitMQ / RocketMQ 的设计，最后回扣"为什么消息队列里有这么多并发技巧"。

---

## 一、总起：为什么从"订单超时"开始

几乎所有电商系统都有一个需求：**订单创建 15 分钟后如果还没付款，自动取消并释放库存。**

最朴素的实现方式：开个定时任务，每隔 60 秒查一次数据库，把超时订单关掉。

这篇文章就从这个"定时轮询"出发，一步步升级到延时队列。完整代码在 GitHub：[dailystudy-java](https://github.com/yhg60541-wq/dailystudy-java)

---

## 二、第一步：先看看轮询有多痛（不写代码）

没写一行代码，先算了笔账。

### 轮询的运行逻辑

```
闹钟每 60 秒响一次
→ 查数据库："有没有创建超过 15 分钟、还没付款的订单？"
→ 有就取消 + 回滚库存；没有就白跑
→ 闹钟继续等下一次响
```

### 算一下代价

**问题 1：一天扫多少次？**

一天 = 24 × 60 × 60 = 86400 秒。每 60 秒一次 → **一天 1440 趟**。不管有没有订单，风雨无阻。

**问题 2：一笔订单最坏多久才被取消？**

两段时间：
1. 它要等够 15 分钟才"有资格"被取消
2. 刚好变成 15 分钟那一刻，定时任务可能刚走过，要等下一轮闹钟（最多 60 秒）

**最坏 = 15 分钟 + 60 秒 ≈ 16 分钟**。买家下单后 1 分钟就放弃了，这笔订单对应的库存被白白锁住 16 分钟。

**问题 3：一天只有 10 笔订单的话，空跑多少次？**

1440 次总巡查 - 最多 10 次能查到东西 = **1430 次空跑**。空跑率 ≈ **99%**。每趟都是一条真实的 `SELECT ... WHERE status='UNPAID' AND created_at < ?` SQL，数据库白忙一场。

### 轮询的两大代价

| 代价 | 数据 |
|---|---|
| **延迟** | 订单最坏 16 分钟才被取消，库存被白白锁住 |
| **浪费** | 99% 的巡查是空跑，每趟都是一条查库 SQL |

### 本质问题：两个不同步的钟

订单的钟：创建后开始走 15 分钟，走完才算超时。
定时任务的钟：不管订单，每 60 秒固定响一次。

这两个钟谁也不认识谁。订单可能"刚熬够 15 分钟"，但定时任务刚走过，必须再等最多 60 秒。

## 三、第二步：BlockingQueue — 让生产者和消费者解耦

### 先搞懂：消息队列到底干什么？

用一个"银行取号机"类比整个消息队列的工作方式：

```
生产者 = 来办事的客户 → 按一下取号机 → 号进入队列
消费者 = 柜台工作人员 → 从队列里按顺序拿号 → 办业务

关键：客户和柜台**互不认识**。客户来了取号就走，不用管哪个柜台办、什么时候办。柜台办业务也不用管客户在不在、是不是等得急。
```

对应到代码里，就是 JDK 的 `BlockingQueue`——一个线程安全的、自动协调生产消费的队列。

### 跑出来的真实输出

两个消费者抢 10 条消息：

```
生产者：放了 10 条消息
消费者1 消费了 订单-0
消费者2 消费了 订单-1
消费者1 消费了 订单-2
消费者2 消费了 订单-3
...
消费者1 消费了 订单-8
消费者2 消费了 订单-9
```

### 为什么两条线程不会拿到同一条消息？

`ArrayBlockingQueue` 内部有一把锁：

```java
// ArrayBlockingQueue.poll() 简化源码
public E poll(long timeout, TimeUnit unit) {
    final ReentrantLock lock = this.lock;
    lock.lock();                    // 拿锁：同一时刻只有一个线程能进来
    try {
        E x = items[takeIndex];     // 拿消息
        takeIndex = inc(takeIndex); // 推指针
        count--;
        return x;                   // 解锁后才返回给外面
    } finally {
        lock.unlock();              // 释放锁
    }
}
```

"拿消息 → 推指针"这两步被锁变成了**不可分割的整体**——两个线程不可能同时拿到同一条。

### 消息队列的三大核心价值

**解耦（Decoupling）**：生产者和消费者互不认识、互不依赖。生产者只管往队列里放消息，不管谁来处理、怎么处理。消费者只从队列里取，不管谁发的、发了多少。一个挂了不影响另一个。

**异步（Asynchronous）**：把耗时的操作丢给后台慢慢跑，前端线程立刻返回。比如发邮件、生成报表等耗时操作放队列，用户点击"提交"后 100 毫秒内就看到成功，不用干等几秒。

**削峰填谷（Peak Shaving）**：突发流量先存进队列，消费者按自己的处理能力慢慢排。比如秒杀活动 10000 人同时下单，请求不会直接打在数据库上，而是先进入队列，防止数据库被冲垮。

## 四、第三步：DelayQueue — 让消息"等一会再出来"

### BlockingQueue 的问题

BlockingQueue 里消息放进去，消费者 `take()` 立刻就拿到了。但订单超时需要"**等 15 分钟再处理**"——BlockingQueue 做不到。

JDK 有个专门的：`DelayQueue`。

### 怎么用？实现 Delayed 接口

```java
public class DelayedOrder implements Delayed {
    private final String orderId;
    private final long expireTimeMs;  // 到期的绝对时间戳

    public DelayedOrder(String orderId, long delayMs) {
        this.orderId = orderId;
        this.expireTimeMs = System.currentTimeMillis() + delayMs;
    }

    // getDelay：距离到期还有多久。返回 <= 0 说明时间到了
    @Override
    public long getDelay(TimeUnit unit) {
        long remaining = expireTimeMs - System.currentTimeMillis();
        return unit.convert(remaining, TimeUnit.MILLISECONDS);
    }

    // compareTo：告诉 DelayQueue 谁到期早排前面
    @Override
    public int compareTo(Delayed other) {
        DelayedOrder o = (DelayedOrder) other;
        return Long.compare(this.expireTimeMs, o.expireTimeMs);
    }
}
```

### 跑出来的真实输出（故意乱序放入，看出来序）

```
生产者：放了 5 笔延时订单（故意乱序放的）
消费者：订单-A 到期取消 ✅     ← 最早到期（1秒）
消费者：订单-B 到期取消 ✅     ← 第 2 秒
消费者：订单-C 到期取消 ✅     ← 第 3 秒
消费者：订单-D 到期取消 ✅     ← 第 4 秒
消费者：订单-E 到期取消 ✅     ← 最晚到期（5秒）
消费者：队列空了，退出 ✅
```

放入顺序是 E→C→A→D→B，出队顺序严格按到期时间 A→B→C→D→E。`compareTo` 生效了。

### DelayQueue 内部是什么结构？

它**不是链表**，而是**PriorityQueue（优先堆）**。

### 什么是堆？

堆是一种**完全二叉树**（除了最底层，其他层都被填满，最底层的节点都靠左排列），分两种：

- **最小堆**：每个父节点的值都 ≤ 它的子节点 → 根节点是全树最小的
- **最大堆**：每个父节点的值都 ≥ 它的子节点 → 根节点是全树最大的

`PriorityQueue` 默认是**最小堆**——每次 `take()` 只拿根节点（最小的那个）。

### DelayQueue 里最小堆的样子

放入 5 条延时消息（乱序放的）：E(5s) → C(3s) → A(1s) → D(4s) → B(2s)

PriorityQueue 内部自动堆成：

```
           A(1s)            ← 堆顶，最早到期
          /      \
      B(2s)      C(3s)      ← 第二梯队
      /    \
  D(4s)    E(5s)            ← 最晚到期的在底下
```

每次 `take()` 只拿堆顶，拿完剩下的节点自动重新调整堆结构。所以出队顺序永远是 **A→B→C→D→E**——跟放入顺序完全无关。

### 几个关键点

**getDelay 返回负数是什么意思？**

如果一条订单该 5 秒到期，程序睡了 6 秒才启动消费者——`getDelay` 返回 **-1 秒**。DelayQueue 一看："早就该出了"，立刻给消费者，不等了。

**DelayQueue 不持久化**：它内部的堆在 JVM 内存里，程序一关闭全丢。

## 五、第四步：ConcurrentSkipListMap — 模拟 Redis ZSET

### DelayQueue 的两宗罪

| 问题 | 后果 |
|---|---|
| 重启全丢 | 服务器重启，所有还没到期的订单消息没了 |
| 单机独占 | 两个 JVM 实例各玩各的，各自有一份消息，不共享 |

真实生产不会用 JDK 的 DelayQueue。主流方案是 Redis ZSET——有序集合，按 score 排序，支持持久化，多客户端可以协作。

### 用 ConcurrentSkipListMap 模拟 ZSET

先看 Redis ZSET 的核心特性：
- 按 score（分值）自动排序 → 我们用 `ConcurrentSkipListMap<Long, String>`，key 就是到期时间戳（score），自动升序
- 支持原子取出 score 最小的元素 → 我们用 `pollFirstEntry()`

### 先让它坏：两步操作的空隙

```java
// 有 bug 的写法
Map.Entry entry = zset.firstEntry();  // ① 读：两个 worker 同时拿到 A
if (entry.getKey() <= now) {
    zset.remove(entry.getKey());       // ② 删：两个都删 A → 重复消费！
    print "处理了 A"
}
```

**空隙在哪？** 第①步和第②步之间是两行独立的 Java 代码 → 编译成几十条独立 CPU 指令。操作系统可以在这中间切换 CPU 给另一个线程。

```
时刻     worker1                     worker2                map 状态
───────────────────────────────────────────────────────────────────────
T1      firstEntry()                 firstEntry()           [A, B, C]
        → entry = A                  → entry = A            两个都读到了 A！
        ↓ 还没执行 remove()          ↓ 还没执行 remove()
T2      remove(A)                                           [B, C]
        print "处理了 A"
T3                                   remove(A)              [B, C]
                                     print "处理了 A"   ← 重复！
```

### 正确的写法：pollFirstEntry() 原子抢占

```java
// 正确的写法
Map.Entry entry = zset.pollFirstEntry();  // 原子地"读+删"
if (entry != null && entry.getKey() <= now) {
    print "处理了 A"  // 只有一个 worker 能拿到
}
```

### pollFirstEntry 为什么不会有空隙？

它内部是 **CPU 硬件级 CAS 指令**（`cmpxchg`）：

```
CAS(内存位置V, 预期值A, 新值B)：
  1. 读 V 的值
  2. 如果 V == A → 把 V 改成 B，返回"成功"
  3. 如果 V ≠ A → 什么都不做，返回"失败"
```

这三步在 CPU 里是**一条不可分割的指令**——执行时锁住内存总线，其他 CPU 核心此刻不能读也不能写这块内存。

```
worker1: pollFirstEntry()
         内部 CAS：队首是 A 吗？→ 是 → 删掉 A → 返回 A ✅（CPU 指令级锁死）

worker2: pollFirstEntry()（几乎同时）
         内部 CAS：队首是 A 吗？→ 不是了！被 worker1 删了 → 失败 → 返回 null ✅
```

### 知识会师：CAS 思想的复用

| 场景 | CAS 抢占什么 | 抢占失败了怎么办 |
|---|---|---|
| ConcurrentHashMap 扩容 | sizeCtl 从 12 改成 -1 | 其他线程看到 sizeCtl ≤ 0 → 直接跳过 tryResize |
| 延时任务分发 | 队首 entry 原子删除 | 其他 worker 看到返回 null → 继续等下一个 |

同一个模式：**CAS = "只有第一个抢到的人干活，其他人看到被抢了立刻放弃"**。不管抢的是"扩容权"还是"延时任务"，思路完全一致。

### 关卡 3 跑出来的真实输出

```
生产者：放了 5 笔订单，zset 当前 key 顺序：[时间戳A, 时间戳B, ...]
worker1 处理了 订单-A     ← worker1 抢的
worker2 处理了 订单-B     ← worker2 抢的
worker1 处理了 订单-C     ← worker1 又抢了
worker2 处理了 订单-D
worker1 处理了 订单-E     ← 每条只被一个 worker 处理 ✅
```

### Redis ZSET 到底是什么？

Redis 是一个**内存数据库**——数据主要存在内存里（读写极快），同时可选同步到硬盘（保证不丢）。和 MySQL 的区别：

| 东西 | 数据存在哪 | 速度 | 持久化 | 适合场景 |
|---|---|---|---|---|
| MySQL | 硬盘上 | 慢（每次要读/写硬盘） | 天生就持久化 | 核心业务数据（订单、用户） |
| HashMap | JVM 内存 | 快 | ❌ 程序一关全丢 | 临时计算、单机内部缓存 |
| Redis | 主要在内存 | 极快（单线程+内存操作，每秒扛 10 万次读写） | ✅ 可选同步到硬盘 | 需要快速读写、允许偶尔丢的临时数据 |

Redis 提供 5 种数据结构：String、Hash、List、Set、**ZSet**。我们只关心 ZSet——因为它就是延时队列的核心。

**ZSet = Set + 每个元素多了一个 score（分值）**。普通 Set 是个不重复的集合，但没有顺序；ZSet 每个元素带一个 score，Redis 自动按 score 升序排好。

```
存普通 Set：["订单-A", "订单-B", "订单-C"]  ← 没顺序

存 ZSet：
  (score=1000, "订单-A")   ← Redis 自动按 score 排序
  (score=5000, "订单-B")
  (score=3000, "订单-C")
排序后 Redis 内部：
  (score=1000, "订单-A")   ← 最小
  (score=3000, "订单-C")
  (score=5000, "订单-B")
```

**ZSet 怎么实现延时队列？** score 就是**到期时间戳**。

```
订单-A（15 分钟后到期）→ ZADD timeout_orders (score=当前时间戳+15分钟, value="订单-A")
订单-B（30 分钟后到期）→ ZADD timeout_orders (score=当前时间戳+30分钟, value="订单-B")

ZSet 自动排序 → score 最小的就是"最早到期的"

消费者循环：
  1. ZPOPMIN timeout_orders → 原子地弹出 score 最小的那个 → 拿到最早到期的
  2. 看看弹出来的 score（到期时间戳）是不是 <= 现在
  3. 如果 <= 现在 → 时间到了 → 关单
  4. 如果 > 现在 → 还没到 → ZADD 回去（因为 POP 删了）→ sleep 到下次检查
```

对应我们关卡 3 的代码：
- `zset.put(now + 5000, "订单-E")` 对应 Redis 的 `ZADD timeout_orders (score=now+5000, "订单-E")`
- `zset.pollFirstEntry()` 对应 Redis 的 `ZPOPMIN timeout_orders`

### 真实 Redis 方案对应哪条命令？

**ZPOPMIN key [count]**——原子地弹出 ZSET 中 score 最小的元素。Redis 6.0 之前是**单线程模型**：所有命令按收到的顺序一个一个执行，没有并发问题，天然原子。Redis 6.0 引入多线程，但只用于网络 IO（收请求、发响应），真正执行命令的核心还是单线程，所以 ZPOPMIN 在 Redis 7.x 里依然原子。

为什么我们写的 `ConcurrentSkipListMap.pollFirstEntry()` 也是原子的？因为它底层也是 CAS（compareAndSet）——和 ZPOPMIN "单线程天然原子" 效果相同，路径不同。这就是**并发控制的两种哲学**：
- **单线程模型**：没有并发，自然安全（Redis、Node.js 早期版本）
- **多线程 + CAS**：有并发，靠硬件指令保证原子（ConcurrentHashMap、ConcurrentSkipListMap、现代操作系统内核）

### 四方案对比表

| 方案 | 延迟精度 | 多实例共享 | 重启不丢 | 复杂度 |
|---|---|---|---|---|
| 定时轮询 | 最差（+60s） | ✅ 每个实例各扫各的 | ✅ 扫的是 DB | 最低 |
| BlockingQueue | 立刻触发 | ❌ 单机 | ❌ 内存 | 低 |
| DelayQueue | 精确到毫秒 | ❌ 单机 | ❌ 内存 | 低 |
| ConcurrentSkipListMap | 精确到毫秒 | ❌ 单机 | ❌ 内存 | 中 |
| Redis ZSET | 精确到毫秒 | ✅ 多客户端 | ✅ 持久化 | 中 |

### 什么是持久化？

**持久化 = 把数据写到硬盘上，让它在程序退出后还能活着。**

| 不持久化 | 持久化 |
|---|---|
| 数据在内存里 | 数据写到硬盘（数据库、日志文件） |
| 程序一关闭 → 全丢 | 程序重启 → 数据还在 |
| 速度快 | 速度稍慢（因为要写硬盘） |
| 适合：临时计算、缓存 | 适合：订单、消息、用户数据 |

Redis ZSET 会把数据同步写到硬盘的 RDB/AOF 文件里，服务器重启后能恢复回来。而我们写的 `ConcurrentSkipListMap` 在 JVM 内存里，程序一关延时任务全丢——这就是"持久化"的价值。

## 六、理论关：对齐主流 MQ

### RabbitMQ 怎么做延时？

RabbitMQ 没有"延时队列"这个功能，是用**TTL + 死信队列**拼装的。

TTL = Time To Live（生存时间）：消息在队列里最多能待多久。
死信队列 = 存放"过期消息"的队列，被 TTL 过期的消息自动路由到这里。

```
步骤 1：建一个"暂存队列"（设置 TTL=15分钟，没有消费者）
步骤 2：暂存队列绑定死信交换机 → TTL 到期的消息自动路由到"处理队列"
步骤 3：消费者蹲"处理队列" → 一有消息说明 15 分钟到了 → 关单

订单创建时：
  发消息到暂存队列，带上 expiration="900000"（15分钟=900000毫秒）
  
900000 毫秒后：
  消息从暂存队列消失 → 自动进入处理队列 → 消费者收到 → 关单
```

这个方案的代价是延时精度不高——TTL 到了之后还要等 RabbitMQ 路由过期消息，通常会额外延迟 1-10 秒。如果对精度要求高，就不能用这个方案。

### RocketMQ 怎么做延时？

RocketMQ 4.x 用**固定延时等级**：只有 1s/5s/10s/30s/1m/2m/.../1h/2h 这 18 个等级。想延时 137 毫秒？选最接近的 1 秒。想延时 15 分钟？选 20 分钟。

为什么不能自定义延时？因为 RocketMQ 内部用的是**定时轮询 + 每个等级一个 Topic**，要支持任意延时成本太高。

RocketMQ 5.x 开始支持任意延时时间（内部类似关卡 3 的 ZSET 方案）。

### 消息丢了怎么办？（三个环节 + 兜底）

消息从生产到消费，有三个环节可能丢：

```
生产者发消息 → ① → Broker 存储 → ② → 消费者拿到 → ③ → 业务处理完成
```

**① 生产者→Broker：网络断了**

生产者发消息，但网络抖动，Broker 根本没收到。兜底方案是**生产者确认机制 + 重试**：Broker 收到消息后回一个 ACK（Acknowledgement），生产者如果没收到 ACK，就自动重发。RocketMQ 默认重试 2 次。RabbitMQ 用 publisher confirm 机制实现。

**② Broker→消费者：消费者挂了**

Broker 里存了消息，消费者通过网络拿到了，但还没来得及处理完就挂了。Broker 不知道这个消费者到底处理完没，保险起见，**等一段时间后把这条消息重投给其他消费者**。兜底方案是**消费者手动 ACK**：消费者处理完业务逻辑后，显式告诉 Broker"我处理完了"。如果消费者挂了（没发 ACK），Broker 才会重投。注意不能"拿到就 ACK"——那样消费者挂了消息就真丢了。

**③ 消费者处理中：业务没做完**

消费者已经拿到了消息，也开始处理了，但业务逻辑还没执行完（比如还没 commit 数据库事务）就挂了。兜底方案是**把业务逻辑包在事务里 + 本地消息表**：
- 简单方案：整个处理逻辑包在 `@Transactional` 里，业务没做完事务不提交，回滚到之前的状态
- 复杂方案：用"本地消息表 + 定时扫描补偿"——业务处理和"标记消息已处理"写在同一个事务里，定时任务扫描"处理到一半挂了"的消息，重新投递

### 消息重复消费怎么办？（幂等性）

重复消费**一定会发生**——因为 Broker 的重投机制：消费者处理超时或挂了，Broker 不知道到底处理完没，保险起见重投一条。消费者必须自己保证"重复处理同一个消息不会造成脏数据"。

这个保证就叫**幂等性（Idempotency）**：同一件事做 1 次和做 100 次，结果一样。

常见幂等方案：

**方案 1：唯一索引拒重复写入**

给一个业务上天然唯一的 ID 建唯一索引。比如下单时 `(user_id, request_id)` 建唯一索引，不管 MQ 重投多少次、用户重复点多少次，只有第一次能 insert 成功，后面的全被 DB 拒绝。

```java
try {
    orderRepo.insert(...);  // 第一次成功
} catch (DuplicateKeyException e) {
    // 唯一索引冲突 → 说明这条 requestId 已经下过单了
    // 回滚已扣的库存 + 返回已存在的订单
    listingRepo.incrementStock(listingId, qty);
    return existingOrder;  // 不重复扣库存
}
```

**方案 2：状态机 CAS 跳过已处理的**

业务流转带明确的状态前置条件。比如关单逻辑只有状态是 "UNPAID" 才能改成 "CANCELLED"：

```java
int n = orderRepo.compareAndSetStatus(id, "UNPAID", "CANCELLED");
// 如果已经是 CANCELLED（被第一次关单改过了）→ n=0 → 跳过，不回滚库存
if (n > 0) {
    listingRepo.incrementStock(listingId, qty);  // 只有 CAS 成功才回滚
}
```

**方案 3：分布式锁**

同一条消息只能有一个消费者实例处理。用 Redis 的 `SETNX` 或数据库行锁实现"同一订单号同时只能被一个实例拿到处理权"。

| 方案 | 核心思路 | 适合场景 |
|---|---|---|
| 唯一索引 | DB 层面拒掉重复写入 | 下单、支付（有明确唯一 ID） |
| 状态机 CAS | 业务层面跳过已处理的 | 关单、改状态（有明确状态前置条件） |
| 分布式锁 | 同一条消息同时只能一个实例处理 | 复杂业务流程，没有天然唯一 ID |

## 七、复盘：五句话讲清延时队列

1. 定时轮询有两大问题：**延迟大**（最坏 +60s）和**浪费多**（99% 空跑）。本质原因是"两个不同步的钟"。
2. DelayQueue 内部是**最小堆**（PriorityQueue）——完全二叉树结构，`compareTo` 决定排序（到期早的排堆顶），`getDelay` 决定能不能出队（<=0 才能出）。
3. 多实例抢延时任务，核心是**原子抢占**——不能"读+删"两步做，要像 `pollFirstEntry()` 那样一步完成，底层是 CAS 硬件指令。
4. CAS 思想贯穿所有并发场景：不管抢的是"扩容权"还是"延时任务"，模式都是——**"只有第一个抢到的人干活，其他人看到被抢了立刻放弃"**。
5. 消息队列三大核心价值：**解耦**（生产者不管消费者）、**异步**（慢活放后台）、**削峰填谷**（突发流量存起来慢慢排）。

## 八、常见问题解答

**Q1：延时队列和定时任务扫表，到底选哪个？**

轮询适合**低 QPS、能容忍延迟**的场景。比如每天凌晨扫一次过期优惠券，一天一次、延迟几个小时没关系——用定时任务完全够用，引入 MQ 反而增加复杂度。

延时队列适合**高 QPS、延迟敏感**的场景。比如订单超时、支付回调超时——每 15 分钟就有一批，库存被白白锁住 16 分钟影响销售，延时队列毫秒级触发才有价值。

一个实用的判断标准：**如果你的定时任务 QPS < 1，扫表成本可以忽略，用轮询就行；如果 QPS 很高且延迟敏感，上延时队列。**

**Q2：为什么不直接用 JDK DelayQueue？**

三个硬伤：① 不持久化（JVM 重启全丢）② 单机独占（起两个 JVM 各玩各的）③ 不支持多 worker 原子协作。真实生产用 Redis ZSET（`ZADD` 存延时、`ZPOPMIN` 原子取到期）或 RocketMQ 延时消息。

**Q3：Redis ZSET 的 ZPOPMIN 为什么能原子？**

Redis 6.0 之前是**单线程模型**——所有命令按收到的顺序一个一个执行，没有并发问题，天然原子。Redis 6.0 引入了多线程，但只用于网络 IO（收请求、发响应），真正执行命令的核心还是单线程。所以 `ZPOPMIN` 在 Redis 7.x 里依然原子。

**Q4：幂等除了唯一索引和状态机，还有什么方案？**

还有两种常见的：
- **本地消息表**：在同一个数据库事务里同时做"业务写入"和"写一条消息表记录"。消费时先查消息表有没有这条，有就跳过。定期扫描"业务做了但消息表没标记"的，补偿处理。
- **防重 token**：调用方先向服务端申请一个唯一 token，真正写操作时带上这个 token，服务端用 token 做唯一键防重复。支付宝支付就是用这个方案。

但**唯一索引和状态机是最简单、最可靠的**，优先考虑这两个。

**Q5：消息积压了怎么办？**

积压 = 消费者处理速度 < 生产者发送速度。排查和处理的思路：
1. **先扩容消费者**：最简单直接的办法——增加消费者实例数。消息队列的消费者天然可以水平扩展。
2. **优化单条处理速度**：消费者内部有没有 DB 慢查询？能不能用异步 IO？能不能把多次 DB 操作合并成批处理？
3. **临时降级**：如果积压的是非核心消息（比如日志、通知），可以临时丢弃部分，保证核心业务消息先消费完。
4. **根因治理**：为什么积压？是突发流量（秒杀过后就没了）还是消费者代码有 bug（处理一条卡 30 秒）？后者要先修 bug 再扩容。

**Q6：持久化和缓存的区别？为什么需要两者？**

持久化（MySQL 存订单、Redis AOF）= 为了**数据不丢**——程序重启、甚至服务器换机还能恢复。但写硬盘慢。

缓存（内存 HashMap、Redis 不持久化模式）= 为了**读得快**——但程序一重启就没了。

真实系统里两者都要有：核心数据先写持久化，再放一份到缓存里加速读取。

**Q7：CAS 和 synchronized 有什么区别？什么时候用哪个？**

| 对比项 | CAS | synchronized |
|---|---|---|
| 机制 | CPU 硬件指令（原子读-改-写） | JVM 管的监视器锁 |
| 失败了怎么办 | 立刻返回 false，调用方自己决定重试还是放弃 | 线程阻塞，等锁释放自动唤醒 |
| 性能 | 无锁，不阻塞，不挂起线程 | 锁竞争时线程挂起/唤醒，成本高 |
| 复杂度 | 调用方要写循环重试逻辑 | JVM 自动管，写起来简单 |
| 适合场景 | 低冲突场景（抢扩容权、抢延时任务） | 高冲突场景（秒杀扣库存） |
